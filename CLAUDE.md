## Architecture
1 loop (`src/agent/loop.ts`), 2 models (fast router/rewriter in `src/agent/router.ts`, main writer), 1 tool (`web_search`), 1 dated memory. Flagship only for hard questions. Shared interfaces in `src/types.ts` (`Message`, `SearchResult`, `ModelAdapter`) come first.

## Memory design (target; the company is about memory and context management)
Today: flat JSON file (`src/memory/store.ts`); the loop pastes a whole day's raw chat into the prompt. Slow and costly as history grows. Target, in build order:
1. **Notes, not transcripts.** After each answer, a background fast-model call writes a small dated note: topic, claim, sources, search query, volatility (pricing = volatile, a capital = stable). Retrieval injects a few short notes instead of raw chat.
2. **Re-check ledger.** For volatile claims store the query plus a snapshot of key values (e.g. prices). "What changed since last Tuesday?" = rerun the stored query, then give the answer model the saved snapshot and today's results to compare in a then / now / status table. (Until 2026-11-15 a second fast-model call extracted today's values and code diffed them; see the status log for why that was removed.)
3. **SQLite store** (`better-sqlite3` or `node:sqlite`) with indexes on date and conversation, plus FTS5 full-text search over notes. Replaces the JSON file behind the same `MemoryStore` interface. Embeddings only if keyword search measurably misses.
4. **Layered retrieval, cheapest first:** date resolver (plain code, free) -> time filter -> FTS over notes -> optional embeddings. Router skips memory when the question has no time/past cue; memory lookup runs in parallel with the router.
5. **Cacheable prompts.** Stable prefix first (system prompt, short profile) so provider prompt caching applies; rolling summary of old turns; fixed token budget per prompt section.
6. **Measure it.** Add prompt tokens and cost per question to `bench/`, plus memory-specific questions, and report real numbers in DESIGN.md.
Constraint: the brief allows ONE tool (web search). Memory (including any future internal-docs ingestion) must stay memory the loop reads automatically, never a second tool.

## Future roadmap (post-challenge)
1. **Hybrid semantic recall.** Keep fast SQLite FTS as the first retrieval layer, then add cached embeddings for paraphrases that keyword search misses. Choose hosted embeddings for simpler deployment (API key and small usage cost) or a local embedding model for keyless operation (larger download and runtime).
2. **Document RAG.** Parse and chunk user-approved documents into the existing memory ingestion path, attach source/page provenance, apply the relevance gate, and retrieve only the best chunks. Parsing needs no API key; semantic retrieval needs either hosted or local embeddings.
3. **Scale only when measured.** Keep vectors in SQLite at Memnora scale. Consider `sqlite-vec` or a dedicated vector database only after corpus size and latency benchmarks justify another dependency.

**Demo-video future-option talking point:** Memnora currently proves dated conversational memory with SQLite, structured notes, FTS, re-checks, and explicit forgetting. The natural next step is hybrid document memory: preserve the cheap lexical path, add semantic embeddings for paraphrases, and ingest cited document chunks without exposing RAG as a second agent tool.

  What changed and why (all in my area: `src/agent/`, prompts, benches, tests):
  1. **Main answer runs at `effort: "low"`.** No effort was set, and Sonnet 5.5 defaults to `high`: about 70% of its output tokens were hidden reasoning. Replaying the exact captured requests at four settings (median seconds to first word): high 5.6, medium 5.1, low 4.2, reasoning off 1.0. With the re-check answer order below, low drops to about 1.1 s in most runs because the format does the comparing in the open. It still reasons first when it judges the question hard: 6 of 17 re-check runs took 2.7-6.4 s (the 3 November question both times end to end).   2. **Re-checks no longer run a separate extract-and-diff step.** The answer model now gets the note, the values saved with it and today's results, and compares them itself. Reasons: the step cost 2.2-4.9 s before the first word; it reported values missing from today's results as changes (the "Salesforce flagged" answer); making it fast by switching its reasoning off made it copy the old values without evidence and once pick a stale version (26 became 24); and each re-check saved a new snapshot under the original note, so a second re-check compared against the first re-check, not the original day. `diffSnapshots`, `SNAPSHOT_EXTRACTION_SYSTEM` and `buildSnapshotExtractionPrompt` in `src/memory/` are now unused by the app (a unit test still calls `diffSnapshots`). GPT or Aryan to delete or keep.
  3. **Re-check answers follow a fixed order** (in `ANSWER_SYSTEM`): one sentence on what was saved and when, then a then / now / status table with statuses unchanged, changed or not confirmed, then the verdict. "Not confirmed" is never a change. This is what lets the model start writing at once without getting the verdict wrong.
  4. **Routing is in `src/agent/router.ts`.** Two rules (a re-check reuses the saved query; a bare greeting needs no search), otherwise one fast-model call that sees today's date, the last turns and the recalled notes. The keyword rules are gone. On 57 labelled messages (`npm run bench:routing`, about $0.004 a run): old code 38 right (13 needless searches, 5 missed searches, raw sentence used as the query 30 times); new code 57 right in two separate runs. Routing costs about 1.1 s (p90 1.5-2.1 s) on the messages that reach the model, which is nearly all of them now. A rule may only fail toward searching: I removed my own "memory question, so no search" rule after it missed "have any of those prices gone up?".
  5. **The preview race is removed.** With the first word at about 1 s after the search, the one-sentence fast-model preview (1.4-3.2 s) can no longer arrive first. `web/` still has its rendering code and CSS, now unused.
  6.
